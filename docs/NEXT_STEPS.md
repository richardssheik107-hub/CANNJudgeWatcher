# 首次真实部署验收 / Codex 接手清单

## P0：从可运行原型到可信的真实榜单

1. 在能访问 CANNJudge 的机器执行 `python -m watcher discover`。记录京津东北、星辰杯各赛段实际 ID、slug、组别、起止时间。把关键词选择收敛为准确 slug；不要猜 B 组地址，也不要混合初赛与决赛。
2. 运行一次 `poll` 并导出脱敏快照。人工抽查两场赛事各至少 3 个队伍：官方总分、原始 rank、单题 score、状态、提交 ID、测试点列表、题目权重。截图中的分数不能充当实时校验样本。
3. 检查总榜与单题榜的 stable ID 是否相同。若一个接口只公开 user ID，另一个公开 team ID，只能使用明确公布的成员映射。不得凭同名、提交者昵称或名次拼接队伍。
4. 若总榜没有 rank，本版明确显示未知并提供非官方参考名次。验证官方排序、权重和并列规则后，才增加标记清晰的官方规则复算模式。不能把加速比或任何油猴自定义分数直接当官方总分。
5. 检查官方 score 是否使用移动全场基准。当前峰值模式刻意保留历史出现过的分数；统一基准重评分是另一种模式，需要完整已验证公式、基准和有效提交证据。两者禁止混称。
6. 使用 Docker 常驻运行 24 小时，确认故障不清空当前榜、限流会退避、数据库卷持续增长、重启后历史不丢。验证 backup 可恢复；避免 `down -v`。

## P1：历史覆盖与运行质量

- 逐步回补当前公开的提交列表。记录覆盖区间、页数限制、最早提交时间、未关联身份记录和接口权限；补录记录没有官方 score 时不加入峰值排名。
- 增加可选外部告警（仅数据退步/新峰值/断流信号，不自动定性藏分），根据公开比赛规则设置频率。
- 对已结束赛事降低轮询频率；当前默认依照配置筛选并轮询，推荐精确选择仍需关注的赛段。
- 大数据量时优化 board 查询、历史分页与导出内存；当前从去重证据计算峰值，适合先验收少数赛段，不宣称已经过大规模压测。
- 增加主办方撤销/违规成绩失效流程。历史证据留存，但失效记录应可从可用峰值中排除，并保留原因与操作审计。
- 浏览器在网络可用环境补跑真正 HTTP 端到端测试与 Docker 构建测试；本地仅完成 FastAPI TestClient 桥接的浏览器交互测试。

## 不要改变的边界

只读、不交卷、不自动切换账号、不绕过认证/封榜、不请求选手私有代码；不修改原始历史证据、不伪造缺失分数、不把采集开始时间之前的记录说成已覆盖。演示库和生产库始终分离。
